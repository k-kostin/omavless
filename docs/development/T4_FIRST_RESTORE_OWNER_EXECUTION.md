# Inactive first-restore owner execution

Base: #588, `e5eb5828a825741438e292cd2b59ad55b4235741`.

This private normal-compiled composition connects authenticated first-cycle
native-owner preparation and staging to the real two-file executor. It adds no
command, listener, frontend, normal dispatcher, historical startup exception,
successor admission or receipt provider. Ordinary backup/restore remains
unavailable. The existing ordinary owner is borrowed exclusively; no detached
session, owner, stage or reusable effect capability escapes the operation.

The encrypted input is opened and authenticated before acquiring the migration
lease. One uninterrupted lease then spans original boundary capture, exact
owner/revision/generation and Off/idle admission, original-pair preparation,
exclusive staging, real live-file replacement and final readback. The original
authenticated `OpenedBackup`, startup-disabled incoming store and exact old pair
remain alive throughout. This path checks the existing startup-receipt contract
and retains its original member identity; it neither captures a new manager
epoch nor mints a receipt or replaces ordinary production-owner admission.

Only the staging writer can construct `CreatedStage`, retaining the actual
exclusive-created member descriptors plus parent/directory descriptors and the
planned stage identity. It rechecks the exact member set and original inode
metadata after each callback, including the final callback before return. A
post-return recapture cannot substitute for these originals. Existing staging
callers retain their unit result. The new internal result is not itself owner
authority and contains no write or cleanup method.

The private owner gate permits only that retained stage, checks every unrelated
restore/routing fence, and delegates intent/terminal and live old/mixed/new
progression to the existing executor's transaction-bound checks. Before staging,
all pending evidence and fixed replacement slots must be absent. Original
owner/desired/login and private-directory identities remain pinned; original
live-member identities are additionally pinned throughout staging, before the
executor's deliberate replacements. Fresh host observations and exact owner
revision/idle checks repeat at the actual executor gates.
Existing batch-instance identity, including absence versus presence, is retained
separately from revision. Journal semantics still belong to the lower executor:
this slice does not claim original-created-inode protection for its intent or
terminal records beyond that executor's existing checks. The newly continuous
creation-descriptor guarantee covers staged members; the boundary pins cover
owner/desired/login members and private directories.

The sole success is `CommittedStillFenced`. On any failure after entering the
stager, the owner is blocked and close confirmation is invalidated; no automatic
retry, rollback, stage deletion, fence retirement or authority restoration
occurs. A successful commit also blocks that owner's future mutations, because
its backing store changed and the stage/journal remain fences. Explicit Abort
recovery is a separate future authenticated owner integration; existing lower
rollback/crash tests are retained, not represented as new owner Abort support.

## Evidence and remaining boundaries

Focused synthetic fixtures exercise actual encrypted input, exclusive staging
and both real live replacements under the owner gate. They check same-lease
contention, exact resulting/old bytes and retained ordinary startup refusal.
Counterexamples substitute a same-byte stage member in the last staging
callback, drift owner/desired/revision, insert queued work, lose host readiness,
or introduce unrelated evidence before and after the first real replacement.
Late failures preserve the actual partial outcome rather than fabricating an
automatic rollback. Wrong passphrase and pre-existing history create no stage.
Test hosts panic on lifecycle effects; these are filesystem/owner composition
checks, not installed core, System epoch, VM or physical power-loss acceptance.
Source-retention checks protect wiring only. Exact source/build/check receipts
belong to the owning Draft PR.

Still required before product activation: explicit private transfer and
passphrase/confirmation UX, encrypted-format/template compatibility review,
installed exact-head restore/recovery/upgrade/downgrade acceptance and the
separately reviewed ordinary registration policy. Same-generation historical
admission, missing/new-manager receipts and ownership rollover are not decided
here. #586's real System mechanism and #588's late-epoch negatives retain their
own exact-source evidence; this cut does not relabel either as product restore.
