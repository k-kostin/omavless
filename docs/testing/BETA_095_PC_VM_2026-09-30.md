## VM result

The pre-update owner reported Disconnected with desired Disconnected, and
`Meta` was absent. The user runtime was stopped. The package guard correctly
refused the stopped broker's preserved socket. After confirming an inactive
broker, `MainPID=0`, FD store zero, empty private journal, no core, TUN or
socket listener, the exact inactive socket node was removed interactively in
the VM; the unchanged guard then passed. Both exact-version packages installed
in one ordinary `pacman -U` transaction. The already activated native owner
and saved profiles were preserved. The matching native-only frontend replaced
the enabled local plugin without starting a tunnel.

The broker and user runtime restarted. The installed `/usr/bin/omavless` hash
matched the reviewed native build record. Final status remained Disconnected,
desired Disconnected, Rule mode, no transition and no `Meta`; both services
were active with broker FD store zero. The installed terminal UI opened and
closed without stopping the runtime. Its Connections, Diagnostics, Rules and
Providers pages rendered in the disconnected state. The Subscriptions page
made one explicit provider-information request on `u`; it reported that usage
was absent or unusable without changing the server list or VPN. Leaving and
returning to the page discarded that private result. No profile names, URLs,
account counters or raw logs were recorded here.

The test-only short Unix-socket fixture correction from #382 was replayed on
the beta task branch after this install. With `CARGO_TARGET_DIR` and `TMPDIR`
under the home directory, `./tests/run-rust.sh` passed there; it changes no
installed runtime bytes. The earlier base-head local run failed only in ten
`SocketUnavailable` fixture cases because their Unix paths exceeded the limit.
`./tests/run.sh` also passed on the task branch. Its private-file fixture tests
used a small, removed scratch directory outside the home Git worktree; this
developer account has a `.git` marker at the home root, so placing those
synthetic private files anywhere below home correctly refuses them. Cargo build
output remained under home, not `/tmp`.

## Extended connected development cycle

The same installed app/DNS/frontend triple was exercised in the same VM with
the existing private store; no package or frontend replacement followed. Before
Connect, direct IPv4 HTTPS by address and DNS name both returned 200. The first
two standalone selections reached reported Connected and created one `Meta`
interface, but TUN HTTPS did not complete. This was not accepted as a working
connection. The guest had default-deny incoming UFW and no `Meta` exception.

After inspecting the current guest rules, the operator added only a temporary
VM rule permitting inbound `Meta` traffic to its fixed `198.18.0.1` address.
One standalone selection then progressed from timeout to TLS EOF; it still did
not count as working-server evidence. The installed TUI completed one explicit
all-profile, no-TUN HTTPS probe job for 37 profiles. At least three responsive
entries were visible in the final viewport. One responsive subscription entry
was selected without exporting its name or credential. In Rule mode, reported
Connected agreed with a route through `Meta`; both IP-target and DNS-name IPv4
HTTPS returned 200 with TLS verification, and the externally observed exit path
differed from the later direct baseline. This is a bounded working TUN path in
the isolated VM, not proof of every routing rule, IPv6 or every server.

While connected, the installed TUI rendered Traffic, Details, Connections and
Diagnostics in English and Russian at 100×40, plus the Russian diagnostics and
primary controls at 78×28. The sampled rendered lines fit their terminal width;
neither raw VLESS URIs nor UUID-shaped credentials appeared in the inspected
views. Sixteen concurrent read-only CLI snapshots all retained Connected,
the same native owner and no active transition. These checks do not substitute
for a full connected stale-private-view or multi-client mutation gate.

The VPN was explicitly disconnected, `Meta` disappeared, the temporary UFW rule
was deleted and its absence verified, and direct HTTPS again returned 200. A
disconnected user-runtime restart with the TUI still open changed runtime
instance identity; the TUI recovered a Disconnected view without connecting or
showing a raw credential. The TUI was then closed. Final desired and actual
state are Disconnected, Rule mode, native ownership, no transition, two baseline
interfaces and no temporary UFW exception. The physical PC was untouched.

A later VM-only attempt left the installed TUI on Connections while a second
client disconnected the previously responsive selection. The current attempt
reached Connected but neither IP-target nor DNS-name HTTPS completed; even
with the same narrow temporary `Meta` allowance, no active connection row was
captured. After the second client disconnected, the open TUI showed unavailable
connection data rather than retaining its earlier zero-row count. This does
**not** satisfy the connected stale-private-row gate because there was no
private row to clear. Desired/actual returned to Disconnected, `Meta` was
absent, the TUI closed, and the temporary VM firewall rule was deleted and
verified absent again. No physical-PC network state changed.

## Completed x86_64 installed T3/T4 beta checks

The unchanged installed app/DNS/frontend triple above was exercised again in
the same x86_64 VM. This remains agent-run beta evidence, not owner-attended RC
acceptance. While the TUI was on Connections at 100×40, a synthetic loopback
HTTP request used the owned core's local mixed port and held one connection.
The page showed `Active connections: 1`. A second semantic CLI client then
disconnected OmaVLESS. The open page changed to `Unavailable` rather than
retaining the old private row; desired and actual state were Disconnected and
the TUN was absent. This closes the previously missing **nonempty-row**
stale-view development check without relying on an external VPN server.
The same beta source now has a deterministic nonempty-row regression: if a
replacement runtime instance brackets a late Connections reply from the old
instance, the TUI refuses the refresh and drops the prior private snapshot.
That is source evidence, not a claim that a connected installed runtime was
crash-restarted. The earlier disconnected installed restart remains separate.

In a separate disconnected test, the TUI prepared a confirmed Connect for a
selected profile. Before confirmation, the CLI changed the mode from Rule to
Direct, advancing the shared revision. The stale TUI confirmation reported a
changed action and did not connect. The mode was restored to Rule, the TUI
closed, and no tunnel remained. This is one installed conflicting-client
mutation fence, not a blanket proof of every concurrent operation.

For T4, a temporary loopback-only HTTP fixture served a valid synthetic feed
and either a bounded `Subscription-Userinfo` claim or no such header. A test
subscription was added through the normal semantic CLI while VPN remained
Disconnected. The installed TUI's explicit `u` read displayed
provider-attributed usage in English. Changing only that synthetic URL through
the CLI immediately cleared the previous private result; the next explicit
read showed “not provided” without changing the VPN. Leaving and reopening
the page discarded the result. The negative and positive states were then
rendered in Russian; at 78×28 the positive heading remained visible and
captured lines fit the viewport. No raw URI, UUID-shaped value or fixture URL
appeared in the reviewed viewport. Deleting the selected test subscription
from the CLI removed its displayed claim. The fixture server and disposable
file were stopped/removed, and subscription/profile counts returned to their
original values. No real subscription or credential was copied into a test
file or shareable output.

The source-only late-row regression and these evidence updates passed the full
developer suite (498 Python tests, two expected skips, plus QML and UI
contracts), full Rust suite including format, Clippy, PTY and parity checks,
and documentation navigation. The Rust suite uses a short private temporary
directory to keep its synthetic Unix sockets below the platform path limit.

These results cover the installed transport/owner/TUI path against a synthetic
provider. The existing real provider did not offer a usable usage claim in the
earlier read, so compatibility with an external provider that does offer one
is **not** claimed. That distinct product-maturity observation remains open;
it does not invalidate the bounded transient beta behavior above. Final VM
state again was Disconnected/Rule, no `Meta`, no temporary firewall exception,
no test subscription or listener, and direct IPv4 HTTPS returned 200 with TLS
verification. The physical PC was untouched.
