# OmaVLESS localization foundation

Status: I1 foundation implemented, 2026-08-28. English is the complete
fallback and Russian is the first additional UI locale. This checkpoint does
not claim that every historical surface is translated.

## Architecture

`I18n.js` is the small QML-side catalog and lookup boundary. Stable semantic
keys are grouped by purpose:

- `status.*`, `action.*`, `common.*` — common state and controls;
- `mode.*`, `routing.*`, `metric.*`, `traffic.*` — connection presentation;
- `profiles.*`, `subscriptions.*`, `settings.*` — product surfaces;
- `import.*`, `subscription.*` — confirmation flows;
- `error.*` — the stable v1 control-protocol error codes.

English is required for every key. `ru`, `ru_RU` and `ru-RU` select Russian;
any other or missing locale selects English. A missing key produces visible
bounded English text (`Missing translation: …`) rather than an empty control.

Interpolation accepts only named placeholders already present in the trusted
catalog string. Values are control-character-normalized and bounded to 160
characters; complete output is bounded to 512 characters. Dynamic values are
rendered through the project's `PlainText` sinks or the existing tooltip
sanitizer, so markup in a profile/provider/search value remains inert.

## Locale policy

Settings exposes a persisted `System` / `English` / `Russian` selector. System
follows `Qt.locale().name`; unsupported system locales fall back to English.
Changing the selector updates QML bindings in place. It does not reload the
plugin, restart the shell, call the backend or alter the requested/actual VPN
state. The stored value is only the bounded `system`, `en` or `ru` enum and
never mutates the operating-system locale.

The process environment variable `OMAVLESS_LOCALE` remains a bounded
support/QA override used for exact-head acceptance without changing the host
locale or persisted user choice. It accepts no path or code and unsupported
values still produce English.

## String inventory and ownership

### Translated in I1

- main connection actions and connected/disconnected labels;
- Full VPN, Routing and Direct mode choices;
- main metrics, traffic heading and observed-exit explanation;
- Profiles search/empty states and Subscriptions entry;
- Settings navigation headings and primary action labels;
- Subscriptions page heading, counts, add/help/empty states;
- profile import preview, field labels, TLS/credential privacy notice and
  common confirmation controls;
- subscription add/edit/file confirmation and credential warning;
- three-step onboarding and login-autoconnect configuration;
- routing tools and first-use routing-preset confirmation, while rule payloads,
  targets and unknown preset metadata remain untranslated;
- advanced diagnostics headings, controls, counts and empty/loading states,
  while controller/provider/rule fields remain untranslated;
- the accepted v1 control-plane stable error-code fallbacks.

### Human-authored follow-up batches

- QR/export/rename/delete secondary flows;
- remaining dynamic status prose currently produced by `Service.qml` and the
  legacy Python backend;
- accessibility/tooltip descriptions which are not part of the initial
  coherent surface.

These are I1b/I1c batches, not permission to translate raw backend exceptions.
Backend migration should introduce a stable code plus safe English fallback in
bounded groups, then render the code through the same catalog.

### Never translated

- profile and subscription/provider names;
- endpoints, hostnames and IP addresses;
- transport, protocol and core-defined identifiers where changing the token
  would make diagnostics/configuration ambiguous;
- provider subscription content and core-controlled rules;
- raw logs, controller output and diagnostic payloads;
- URIs, UUIDs, passwords, keys and subscription URLs.

Names may be interpolated unchanged into trusted surrounding grammar, but are
never used as catalog keys or rewritten.

## Testing contract

`tests/test-i18n.js` covers locale normalization, English/Russian lookup,
unsupported-locale fallback, missing keys, bounded interpolation, control
characters, provider/profile pass-through and the complete reserved v1 error
set. QML contracts verify that translated dynamic text remains in `PlainText`
or sanitized tooltip paths and that the installed plugin includes the catalog.

Exact-head UI acceptance covers English and Russian main/settings/import/
subscription flows, longer-label layout, connect/disconnect behavior and the
absence of credential/provider translation or disclosure.

`qmllint` is used when the Omarchy QML import environment provides it; its
absence alone is not an acceptance blocker because the installed-shell smoke
loads the exact production import graph.

## Context-first translation workflow

Translation starts from the product, not from an isolated batch of catalog
values. Before adding or substantially reviewing a locale, record the intended
audience, voice, formality, terminology and any deliberate untranslated
technical tokens. Inspect each key where it is rendered, its neighboring
controls, related screens and every state which can change its meaning. English
and an accepted existing locale provide semantic context; neither is a license
to translate private provider content.

The locale note should identify non-obvious language rules which affect this
product. For Russian this includes formal neutral UI wording, three plural
forms and sufficient room for longer action labels. A future locale note must
also address its relevant number, date, currency, quotation, non-breaking
space, casing, normalization, line-breaking and bidirectional-text behavior.
Do not build compound prose by concatenating translated fragments where the
language may need a different word order. Dynamic technical values should enter
a trusted full-sentence template through named bounded placeholders.

## Visual acceptance loop

Static review cannot reveal every truncation, stale English fragment, bad line
break or contextually wrong translation. Every meaningful locale batch follows
this loop on the exact installed candidate:

1. inventory the changed keys and map them to screens, controls and states;
2. mark high-risk captures in advance: long labels, interpolation, plurals,
   scrolling content, confirmation/error states and mixed technical text;
3. capture or visually inspect the complete affected matrix after animations
   and asynchronous loading have settled;
4. review every capture for meaning, consistency, blank/fallback text,
   clipping, overlap, unexpected elision, line breaks, focus/hover state and
   inert treatment of dynamic text;
5. fix catalog, formatter or string construction at its owning boundary;
6. repeat the affected captures, plus one adjacent regression state. A full
   recapture is required only when shared layout or translation infrastructure
   changed broadly.

For the current panel the baseline matrix is:

| Surface | Required representative states |
| --- | --- |
| Main | disconnected, connected, busy/test, empty profiles, populated and expanded subscription |
| Settings | capability ready and unavailable where reproducible, routing cards, scrolled diagnostics/privacy section |
| Profile import | clipboard/file title, safe preview, validation error, confirmation |
| Subscription import | clipboard/file title, hidden URL, duplicate/error, confirmation |
| Subscriptions | empty, populated, update/test in progress, representative result |
| Dialog behavior | keyboard focus, Escape/cancel, confirmation, longest translated label |

Long scroll surfaces require enough overlapping captures to inspect every row;
one viewport is not evidence for content below it. English fallback and Russian
must both be exercised. An unsupported-locale test proves English fallback but
does not require another complete visual pass when it renders byte-for-byte as
English.

Quickshell currently has no deterministic equivalent of a mobile fastlane
screenshot suite. Human capture is therefore accepted Try Omarchy evidence,
with deterministic QML/catalog contracts covering what can be proved without a
display. Add automation incrementally only when it can wait for stable panel
states and reproduce them without private credentials; do not create a brittle
150-image ceremony which cannot establish the state it claims to show.

## Screenshot privacy

Ordinary acceptance screenshots are private by default. A panel can contain a
profile/provider name, endpoint, hostname, IP address or other fixture-derived
metadata even when credentials are correctly hidden. Such a capture may be
inspected locally as private evidence but must not be attached to a PR, issue,
public result or `docs/testing` report.

A capture is shareable only after an explicit visual privacy audit confirms it
contains no private profile/provider identity, endpoint, URI, UUID, password,
key, subscription URL, controller secret or reusable diagnostic detail. Folder
names such as `shareable` do not constitute that audit. Prefer a deliberately
sanitized fixture/state over image redaction; if redaction is necessary, retain
the unredacted original outside Git and verify the exported pixels rather than
trusting a hidden overlay layer.

Record visual results as a redacted screen/state matrix and the exact tested
commit, not as a dump of private screenshots. After acceptance, restore the
normal locale policy, disconnect any test tunnel and confirm the ordinary
runtime invariants.

## Formatter and future-locale gate

Before enabling a language with materially different formatting or direction,
audit all string construction for:

- locale-aware decimal, percentage, date/time, currency and unit formatting;
- plural categories supported by that language rather than a binary singular;
- language-specific case behavior and Unicode normalization;
- non-breaking spacing and quotation conventions;
- mixed-direction text containing numbers, hostnames or account identifiers;
- grapheme clusters/ZWJ sequences and language-specific wrapping;
- start/end layout semantics, icon direction and keyboard navigation for RTL.

These concerns should be implemented as small tested formatter/layout
boundaries before translating the affected screen. Do not claim RTL support
because the catalog can store an RTL string.
